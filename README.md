# proto

Prototype for an openSUSE baed desktop deployments with a KDE-Linux-inspired
layout. `mkosi` builds a KDE and a GNOME disk image. Each disk has exactly two
GPT partitions:

1. an EFI System Partition containing systemd-boot and a UKI;
2. one writable Btrfs root partition containing mutable state and versioned
   EROFS deployment files.

The packaged operating system is not copied into the Btrfs root. During the
mkosi finalize phase, [`mkosi.finalize.chroot`](mkosi.finalize.chroot) turns
`/usr` into a naked EROFS filesystem at:

```text
/@deployments/<image-id>-<image-version>.<image-arch>.usr.erofs
```

## Boot layout

The UKI embeds all deployment selection in its kernel command line:

```text
root=gpt-auto rootfstype=btrfs rw
system.deployment=<deployment>
rd.systemd.mount-extra=/dev/gpt-auto-root:/sysroot/.system:btrfs:subvol=/,nodev,nosuid,x-gvfs-hide,x-gdu.hide
rd.systemd.mount-extra=/sysroot/.system/@deployments/<deployment>.usr.erofs:/sysroot/usr:erofs:ro,loop,x-systemd.requires-mounts-for=/sysroot/.system/@deployments/<deployment>.usr.erofs
rd.systemd.mount-extra=/dev/gpt-auto-root:/sysroot/etc:btrfs:subvol=/@etc-<deployment>
```

`systemd-gpt-auto-generator` discovers the Btrfs root from the GPT type GUID.
The filesystem's default subvolume is `@root`, so the sibling versioned
`@etc-*` subvolumes and immutable `@deployments` store are not exposed in `/`.
The Btrfs top-level is mounted at `/.system` with desktop disk-utility hiding
hints, making the EROFS backing file available without placing it inside the
resettable root hierarchy.
`systemd-fstab-generator` processes the three `rd.systemd.mount-extra=` entries
in the initrd. Consequently no `fstab` is needed.
The `/usr` entry is ordered after the Btrfs path containing its backing file
and is loop-mounted read-only. After switch-root the mounts become the
installed `/.system`, `/usr`, and `/etc`. `/etc` is versioned with the
deployment, while `/home` and `/var` are ordinary directories inside the
common mutable `@root`. Individual user homes are nested Btrfs subvolumes.
SELinux targeted policy is loaded in enforcing mode. The policy is also part
of the initrd, `/usr` is labeled before it is sealed into EROFS, and the
installer relabels copied mutable state under its final target paths.

The initrd generated by mkosi already includes the `btrfs`, `erofs`, and `loop`
kernel modules. A unit stored in the EROFS image cannot mount that same image,
which is why the old `usr-erofs.mount` approach was removed.

## Building

The configuration requires mkosi 26 or newer and a recent systemd. Its built-in
openSUSE tools tree supplies `erofs-utils`, `python3-pefile`, and the remaining
host-side image tools. Build both desktop variants with:

```sh
PATH="$PATH:/usr/sbin" mkosi -f build
```

Build just one variant (and its `base` dependency) with:

```sh
PATH="$PATH:/usr/sbin" mkosi --dependency= --dependency=base --dependency=KDE -f build
PATH="$PATH:/usr/sbin" mkosi --dependency= --dependency=base --dependency=GNOME -f build
```

Artifacts are written to `mkosi.output/`. Each desktop build produces an
XZ-compressed raw two-partition installation image, the unwrapped standalone
`*.usr.erofs` deployment, an uncompressed split UKI, checksums, and a JSON
package manifest. Only the complete installation disk receives outer XZ
compression. The EROFS filesystem itself is uncompressed so its blocks remain
directly useful for chunked delta transport.

## Live media and installation

Both desktop raw images are live media and installers. Write one directly to
a USB drive (replace the target with the whole USB device, not a partition):

```sh
xzcat mkosi.output/proto-gnome-20260831.x86-64.raw.xz | \
    sudo dd of=/dev/disk/by-id/<usb-device> bs=16M status=progress
sync
```

The raw image contains a build-sized Btrfs partition. On first boot,
`systemd-repart.service` reads `/usr/lib/repart.d/50-root.conf` and expands the
existing root partition over all otherwise unused space on the USB drive.
The partition's Discoverable Partitions `GrowFileSystem` flag then causes
`systemd-growfs-root.service` to grow Btrfs to the new partition boundary. The
same mechanism runs on an installed disk and is idempotent on later boots.

On boot, GDM or SDDM logs in the temporary `installer` account and starts
**Install proto**. The same launcher is available from the application menu
and the live user's Desktop directory. Screen locking is disabled for this
passwordless live account. The first installer supports only one operation:
select a whole writable disk, confirm that all of it may be erased, and
install. The live USB is excluded from the candidates and checked again by
the privileged backend.

The UI is a small Bash/Zenity wrapper. Its privileged half invokes:

```sh
systemd-repart --empty=force --seed=random --copy-source=/ \
    --definitions=/usr/lib/proto/installer-repart.d /dev/<target-disk>
```

Those definitions create exactly a 4 GiB ESP and a Btrfs root, copy
systemd-boot, the UKI, and the EROFS deployment, and create only `@root`,
`@deployments` plus the versioned `@etc-*` subvolume. The installed
`/home` and `/var` start empty inside `@root`. After `systemd-repart`
completes, the installer temporarily mounts `@root` and the versioned
`/etc` and applies the SELinux targeted file contexts before the first boot.
The Btrfs partition has an 8 GiB minimum in addition to the 4 GiB ESP, so
the target disk must be larger than 12 GiB.

The live-only changes in `/etc` are the temporary account's display-manager
autologin, launcher setup, lock-screen policy, and polkit authorization. The
installed `@etc-*` is populated
instead from the sanitized vendor tree in `/usr/share/factory/etc`; it has no
installer account or autologin configuration. The installed system therefore
has no regular user, and GDM starts GNOME Initial Setup after the first reboot
so the owner can create one.

The openSUSE vendor skeleton from `/usr/etc/skel` is first materialized as
`/etc/skel`; the live account is then created with `useradd --create-home`, so
it is copied during the image build. `run0-wrappers` supplies the `sudo`,
`su`, and `pkexec` compatibility commands on top of systemd `run0`. Normal
administrators in `wheel` authenticate with their own password; only the
disposable live `installer` account is authorized without a password.

Installation is destructive.
Test the whole flow in a VM with a disposable second disk before using it on a
real machine.

## Package policy

The `base` subimage contains the shared boot, hardware, networking, update, and
filesystem stack. Desktop images add only a Plasma or GNOME base pattern, a
display manager, a file manager, a terminal, a text editor, and tools that need
direct system access. GNOME therefore includes Disks and GNOME Software;
KDE includes KDE Partition Manager and Discover.

Both software stores are configured for Flatpak. Ordinary applications should be
installed from the store; host-level storage and administration tools belong in
the versioned OS image.

`fwupd` and its UEFI capsule helper are part of the common immutable system.
GNOME Software uses its built-in fwupd plugin, while KDE Discover includes the
dedicated fwupd backend. Firmware payloads and metadata remain writable under
`/var`, but the privileged update engine itself is versioned with `/usr`.

The shared image also includes printing and scanning, Bluetooth and
Thunderbolt, fingerprint readers, common removable/network filesystems, VPNs,
PipeWire codecs, accessibility support, portals, firmware management, and the
desktop-specific integration tools from the Aeon and Kalpa patterns. These are
host capabilities that cannot be repaired reliably by installing an ordinary
Flatpak after the fact.

Power profiles are implemented by TuneD. `tuned-ppd` exposes the
power-profiles-daemon-compatible API expected by GNOME without installing
`power-profiles-daemon` itself.

The top-level package union is retained for OBS dependency resolution; actual
image contents are controlled by the subimages. OBS supports native mkosi
recipes. For OBS-side UKI/Secure Boot signing, add `Include=mkosi-obs` in the
OBS recipe environment and keep the `# needssslcertforbuild` marker.

## Home snapshots

The design follows KDE Linux's current per-user Snapper model. openSUSE's
`useradd` is configured with `BTRFS_SUBVOLUME_HOME=yes`, so every subsequently
created local user's `/home/<name>` is a nested Btrfs subvolume. On the first
login, a `user@.service` drop-in creates `home_<uid>` from the shipped Snapper
template. Users can browse their own `.snapshots` through Snapper's ACLs.

The default retention is six hourly, seven daily, four weekly, and two monthly
snapshots. `snapper-timeline.timer` creates them and `snapper-cleanup.timer`
prunes them. Tracker ignores `.snapshots/.trackerignore`; Plasma's Baloo gets a
system-wide exclusion for the same directory. The live installer account is
excluded. Garbage collection removes a Snapper config only after its home
subvolume has already disappeared; deleting an account alone never deletes
the retained home data.

`/etc/sysconfig/snapper` is mutable Snapper state. It is created by tmpfiles
when absent and deliberately excluded from `/usr/share/factory/etc`, so image
updates cannot reset the list of per-user configurations.

## Containers and future encryption

Distrobox is available directly in both images, using Podman and crun. The
openSUSE branding package provides appropriate defaults, while preserved
`/etc/subuid` and `/etc/subgid` state lets newly created users run rootless
containers. Container and Flatpak SELinux policies are installed as part of
the immutable host.

The images contain the TPM2 userspace libraries and tools needed to inspect
and enroll a TPM later. Disk encryption and TPM binding are not enabled yet:
adding them changes the partition provisioning, recovery-key, PCR/signing,
and update contracts and needs to be implemented as one installer change.

## Updates and rollback

`proto-update` implements the local prepare/activate/rollback boundary.
An update transport writes a verified pair with the same stem to:

```text
/var/lib/proto-update/incoming/<deployment>.<architecture>.efi
/var/lib/proto-update/incoming/<deployment>.<architecture>.usr.erofs
```

The path-activated helper ignores incomplete pairs. For a complete pair it
mounts both the active and new EROFS images, verifies that the immutable
deployment metadata and UKI command line agree, and snapshots the currently
mounted `/etc`. It then applies the new `/usr/share/factory/etc` while the old
system is still running. `.proto-etc-factory.json` records hashes of
vendor-owned files: untouched files receive new defaults, locally changed or
untracked files are preserved, and a vendor-removed file is removed only when
the local copy is still unchanged. Password databases, machine identity,
localization, host naming, `fstab`, `crypttab`, and subordinate-ID databases
are never factory-managed.

The helper commits the EROFS and `@etc-<deployment>` first. Its final atomic
operation publishes the UKI as:

```text
ESP:/EFI/Linux/<deployment>.<architecture>+3-0.efi
```

This is systemd-boot's native boot-counting protocol. Each failed attempt
renames and decrements the entry; after three failures systemd-boot selects a
previous UKI, whose command line selects its matching old EROFS and `/etc`.
After `boot-complete.target` reports no failed system units,
`systemd-bless-boot` removes the counters and makes the deployment permanent.
`proto-update rollback <deployment>` can hide a still-pending UKI
explicitly; it retains the EROFS and `/etc` for diagnosis.

A read-only sync-point snapshot records `/etc` at prepare time. The shutdown
service compares it with the live `/etc` and forwards later administrator
changes into the prepared deployment before rebooting, then refreshes the
sync-point. It is removed after the new deployment has booted, or when the
counted UKI is rolled back/exhausted. This work delays shutdown if `/etc`
changed substantially, but it keeps the next startup free of merge work. An
abrupt power loss after prepare cannot include changes that had not yet reached
the sync service.

`systemd-sysupdate` still has no transactional pre/post hook. Its transfer
definitions must therefore target the incoming directory, not the final ESP
or deployment store; publishing a downloaded UKI directly would bypass the
local transaction. The concrete server URL, signatures, manifests and
Discover transport integration remain distribution/deployment configuration,
but the local hand-off protocol is implemented.

### Delta downloads

Current `systemd-sysupdate` does not generate or consume binary deltas for
regular-file transfers. KDE Linux solves this with `desync`, a `.caibx` index,
and `kde-linux-sysupdated`, which proxies downloads for systemd-sysupdate. The
same design is appropriate here:

```text
usr.erofs -> desync make -> usr.erofs.caibx + chunk store
                         |
systemd-sysupdate -> local proxy -> reconstruct new usr.erofs from local and
                                   remote chunks
```

## Factory reset

The desktop launcher **Factory Reset** starts `factory-reset.target` through
the normal administrator authorization path. systemd stores a
`FactoryResetRequest` EFI variable and reboots. On the following boot,
`systemd-factory-reset-generator` activates `factory-reset-now.target` in the
initrd. Before `sysroot.mount`, `proto-factory-reset.service` mounts the
Btrfs top-level and stages fresh mutable state from each retained deployment's
`/usr/share/factory/etc`.

The reset then switches to a new `@root` and new versioned `@etc-*`
subvolumes. It recursively deletes the old `@root` hierarchy, including
`/home`, `/var`, per-user home subvolumes, Flatpaks, containers, and all other
mutable data. It does not mount or modify the ESP and preserves
`@deployments`, so both the UKIs and retained EROFS images survive.
Factory `/etc` is recreated for every retained deployment, keeping rollback
UKIs bootable. Rename recovery makes an interrupted reset repeatable; systemd
clears the EFI request only after the custom service completes.

The factory-reset UI deliberately refuses to operate on live media. The reset
requires UEFI variable access.
